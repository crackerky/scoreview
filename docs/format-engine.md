# 大会形式エンジンの設計

大会運営者が「大会の形」を決めれば、組み合わせ、試合番号、日程とコート、勝ち上がり、順位決定戦、最終順位までが自動で組み上がり、当日は結果の入力と確定ボタンだけで大会が進む状態を作る。
本書はその中核の仕組みを定める。
運営者の体験から見た要件と優先順位は [operations/operator-experience.md](operations/operator-experience.md)、根拠にした調査は [operations/research-summary.md](operations/research-summary.md) にある。

## 何を自動化するか

参照サイトの運営会社は、348 大会で次の作業を手で行ってきた(clone-spec と取込データの分析による)。

1. チーム数とコート数から大会の形(プールの数と大きさ、順位決定戦の段)を決める
2. シード順に従ってチームをプールへ振り分ける
3. 試合番号(CD)を振り、時刻とコートを割り当てる
4. プールの結果から順位を計算し、同順位帯のチームを順位決定トーナメントの枠へ入れる
5. トーナメントの勝者と敗者を次の試合へ送る
6. 全順位を確定し、大会トップに掲示する

エンジンは 1〜6 のすべてを生成または計算し、運営者は「生成された案を確かめて直す」と「段の結果を確定する」だけを行う。
完全に自動で進めないのは、当日の遅延、棄権、同点の未決といった、規則だけでは決まらない事態が必ず起きるからである(Tournify の Start ボタン、Ultimate Central の Finalize Games も同じ考え方)。

## 基本の考え方:段、グループ、枠、出どころ

大会の形を、次の 4 つの概念で宣言的に表す。

- **段(stage)**:同時期に行うグループのまとまり。例 「予選プール」「順位決定トーナメント」。
- **グループ(group)**:総当たり(pool)かトーナメント(bracket)。既存の `groups` 表の 1 行に当たる。
- **枠(slot)**:グループの参加位置。プールの「A 組の 3 番目」、トーナメントの「1 回戦の上側」など。
- **出どころ(source)**:枠に入るチームの決まり方。次のどれか。
  - `seed(n)`:事前のシード順で n 番目のチーム
  - `group_rank(g, r)`:グループ g の r 位
  - `match(m, win|lose)`:試合 m の勝者か敗者(参照サイトの `[A1-勝ち]`)
  - `band_rank(stage, r, k)`:段の全プールの r 位を集めて並べた k 番目(プールの大きさが不揃いなときの全体順位)
  - `manual`:運営者が選ぶ

エンジンは「形の指定(パラメータ)」から段、グループ、枠、出どころ、試合を生成する。
生成後は、出どころが確定するたびに枠へチームを入れ、そのチームが関わる試合の対戦相手を埋める。

```
形の指定(テンプレート + パラメータ)
   │ 生成
   ▼
段 → グループ → 枠(出どころ) → 試合(CD、左右の枠)
   │                          │
   │ 結果の入力                 │ 時刻とコートの割り当て(日程生成)
   ▼                          ▼
グループの順位 → 段の確定 → 下流の枠が埋まる → 次の試合の対戦相手が決まる
```

## テンプレート

参照サイトの中止を除く 332 ディビジョンのうち 97.9% は、次の 3 つのテンプレートで表せる(取込データの分析)。
形の細部は 160 通りあり、固定の型を並べるのではなく、パラメータで形を作る。

### 1. プール → 順位帯の順位決定(71.4%)

| パラメータ | 意味 | 例 |
|---|---|---|
| チーム数 N、プール数 k | プールの大きさは N/k を基本に差が 1 以内 | 12 チーム、4 プール → 3 チーム×4 |
| シードの配置 | 蛇行(1, 2, 3, 4, 4, 3, 2, 1, …)で各プールへ | USAU と JFDA の標準 |
| 順位帯の分け方 | どのプール順位をまとめて 1 つの順位決定グループにするか | 「1 位」「2 位」「3 位」の 3 帯(4on4 の主流)、「1〜2 位」「3〜4 位」の 2 帯(16 チーム) |
| 帯ごとの形 | 帯のチーム数に応じたトーナメントの型か総当たり | 4 チーム → T4、8 チーム → T8 全順位型、7 チーム → T7(BYE 1) |
| 組み合わせ | 帯の中の対戦の決め方 | たすき掛け(A1-C2、D1-B2、B1-D2、C1-A2)、同順位どうし(A_k 対 B_k) |

参照サイトの直近で最も多い形(2024〜2026 年の 22.4%)は、4on4 の「4 プール(3 チーム)→ 1st / 5th / 9th の T4 を 3 段」である。
運営者は「チーム数」と「コート数」を入れるだけで、この形が初期値として提案される状態にする。

### 2. ノックアウトブロック → 順位ごとの集約(15.1%)

8 チームのトーナメント(ブロック)を複数並べ、各ブロックの同じ順位を次の段で集める。
ビーチの 32 チーム大会(4 ブロック → 1st T4、5th–9th T8、13th–17th T8、21st–29th T12)が代表例である。

### 3. 総当たり 1 段(11.4%)

1 プール、または 2 プール + 決勝プール。順位表がそのまま最終順位になる。

## 規則の詳細

### プールの試合順と試合番号

参照サイトの実データでは、試合番号と試合順に規則がある(取込データの分析 5-4、5-5)。

- 4 チームのプールは 3 ラウンドで、(1-4, 2-3) → (1-3, 2-4) → (1-2, 3-4)。上位シードどうしを最終ラウンドに置く(UPA マニュアル 2.3 の原則と同じ)。
- 3 チームのプールは (1-3) → (1-2) → (2-3)。
- 5 チーム以上はサークル法で生成し、休みが特定のラウンドに偏らないようにする。
- 試合番号は `{グループ文字}{連番}`。グループ文字は大会内の通し(ディビジョンをまたいで続く)。プール内の連番は組み合わせ順((1-2)=1、(1-3)=2、(1-4)=3、(2-3)=4、(2-4)=5、(3-4)=6)で、時刻順ではない。トーナメント内は決勝を 1 として 1 回戦へ向かって振る。

### プール順位(タイブレーク)

順位の基準は大会ごとの設定で、順序つきの基準リストとして持つ。
プリセットを 2 つ用意し、初期値は運営会社の実際のやり方に合わせる。

| プリセット | 基準(上から順) | 根拠 |
|---|---|---|
| 現行方式(初期値) | 勝ち点(勝 3・分 1・負 0)→ 該当チーム間の直接対決 → 得失点差 → 得点 → 運営者の判断 | 参照サイトの 56 プールで全一致(直接対決の有無はデータから判別できなかったので、設定で外せるようにする) |
| JFDA 競技規則 | 勝利数 → 該当チーム間の勝利数 → 棄権試合数の少なさ → 該当チーム間の得失点差 → 共通の相手との得失点差 → 該当チーム間の得点 → 共通の相手との得点 → ブリックマーク投げ(運営者が結果を入力) | JFDA 2025 全日本ミックス競技規則 |

適用の仕方も JFDA に合わせる。
ある基準で同順位の一部だけが分かれた場合は、残ったチームの間で最初の基準からやり直す。
すべての基準で分かれない場合は「未決」とし、勝手に決めない。
未決は運営者の画面に赤で出し、運営者が順位を指定する(ブリックマーク投げやディスクフリップの結果を入れる)まで、その順位を出どころにする枠は埋めない。
未決として出すのも、運営者が指定できるのも、プールの全試合が終わった(結果が入るか未消化になった)後だけにする(試合の途中で並んでいるのは未決ではない)。
指定は、指定した時点の並んだチームと各基準の値に結び付けて保存し、訂正で結果が変わって並んだチームか値が変われば使わずに未決へ戻す(試合前の誤操作の指定や、別の成績のときの指定が後で黙って使われないように)。

### 順位帯をまたぐ全体順位

プールの大きさが不揃いな大会(25 チーム = 4 チーム×4 + 3 チーム×3 など)では、「全プールの 2 位を並べた 3 番目」のような全体順位が要る。
参照サイトではこの順位を画像(暫定順位表)で掲示しており、基準は外から読めない。
そこで、全体順位の基準も設定にし、初期値は「1 試合あたりの勝ち点 → 1 試合あたりの得失点差 → 1 試合あたりの得点」とする(試合数の違いを平均で吸収するため。推測であり、運営会社に確認する)。
自動の結果は必ず運営者の確定を経て使う。

### トーナメントの型

参照サイトで使われている型を、エンジンの部品として持つ(取込データの分析 4)。
各型は「枠の数」「試合と、その勝者と敗者の行き先」「最終的に決まる順位」を持つ。

| 型 | 枠 / 試合 | 決まる順位 |
|---|---|---|
| T4 | 4 / 4(準決勝 2、決勝、3 位決定) | 1〜4 位 |
| T7 | 7 / 9(最上位は 1 回戦免除) | 1〜7 位 |
| T8 全順位型 | 8 / 12(準々決勝 4、準決勝 2、決勝、3 位決定、敗者戦 2、5 位決定、7 位決定) | 1〜8 位 |
| T8 ブロック型 | 8 / 12 | 8 つの順位(それぞれ次の段の枠へ送る) |
| T8 1 回戦のみ | 8 / 4 | 勝者 4 チームと敗者 4 チーム(同順位) |
| T12 | 12 / 6 | 勝者 6 と敗者 6(同順位) |
| T16 | 16 / 20 | 1〜8 位(1 回戦の敗者は別の段へ) |

トーナメント表の格子(画面の罫線)は、型から自動で描く。参照サイトの格子の描き方(clone-spec C 2.3)に合わせる。

### 試合の結果の種類

| 種類 | 扱い |
|---|---|
| 通常 | スコアで勝敗。同点はプールでは引き分け、トーナメントでは勝者を別に指定(サドンデス等の結果) |
| 没収(不戦勝) | 規定スコア(大会の設定。無ければ大会の形の設定。例 15-0)で記録し、棄権試合数に数える。順位計算の得失点は下記 |
| 不成立 | 人数不足など。スコアを記録せず、勝敗だけを記録する(JFDA 規程) |
| 両チーム不戦敗 | 両チームとも負けとして数え、スコアは記録しない |
| 途中打ち切り | 雷や暑さで中断し再開しなかった。その時点のスコアで確定するか、未消化にするかを運営者が選ぶ |
| 未消化 | 時間切れなどで行わなかった。段を確定するときに運営者が「未消化のまま確定」を選ぶ |

不戦勝の得失点は、順位計算(エンジン)では次の順で決める。

1. 記録したスコアがあれば、それで数える(閲覧ページの成績表と同じ値。規定を後から変えても、順位と表示が食い違わない)。
2. 記録したスコアが無ければ、規定スコア(大会の設定、無ければ大会の形の設定)で数える。
3. どちらも無ければ得失点には数えず、勝敗と棄権試合数だけを数える。

記録係の画面は、規定スコアがあればそのスコアで記録し(規定と違うスコアは受け付けない)、無ければ勝者だけを記録する(スコアは本部が後で決める)。
記録と順位計算が同じ規定スコアを使うので、形のあるディビジョンの不戦勝は必ずスコアつきで記録され、1. で数えられる。

参照サイトの 2025 DREAM CUP では 282 試合のうち 88 試合が未消化のまま残っており、時間切れで打ち切る運用が実際にある。
2026 年の米国大学選手権では、速報アプリに不戦勝の選択肢がなく 13-0 で報告されたことが一因となって、失格をめぐる騒動が起きた([S2](operations/research/S2-global-voices.md))。結果の種類は、入力画面の最初の選択肢として出す。

## 段の確定と自動進行

| 出来事 | 自動で起きること | 運営者の操作 |
|---|---|---|
| トーナメントの試合が終了 | 勝者と敗者を次の試合の枠へ入れる。日程と速報に即時反映 | なし(訂正したいときだけ) |
| プールの全試合が終了 | 順位を計算し、未決がなければ「確定待ち」にする | 「確定」を押す。押すと下流の枠が埋まる |
| 段の全グループが確定待ち | 段の全体順位を計算する | 「段を確定」を押す |
| 時間切れ | ― | 「未消化のまま確定」を押す |

プールの確定に運営者の操作を挟むのは、同点の未決、記入漏れ、没収の扱いを、次の段の組み合わせが公開される前に見直す機会を作るためである。
トーナメント内の勝ち上がりは誤りの余地が小さいので自動にする。

### 棄権、時間切れ、中断(本部の一括操作)

- **棄権**: 本部がチームを棄権にすると、残りの試合(試合前で相手が決まっているもの)を相手の不戦勝として一括で記録する(相手も棄権していれば両チーム不戦敗)。確認画面で見た試合と違えば記録しない。棄権したチームが後から順位決定戦に入ると、進行画面の「いまやること」に出す。
- **時間切れ(大会の締め)**: 残りの試合をまとめて未消化にし(相手が未定の試合も)、プールと段を確定する。エンジンが決めなかったチームは、未消化で終わった試合から先で取りえた最も上の順位が同じチームどうしを同順位にする(準決勝が未消化なら 4 チームが 1 位タイ、片方の準決勝だけ終わっていれば、勝者と未消化の 2 チームが 1 位タイで敗者は 4 位)。どの順位決定戦にも進めなかったチームは最後の順位の次に並べる。本部が確かめたうえで最終順位に書き、公開する。未消化の試合は、誰の試合だったかを照合しない(相手が決まる前に未消化にした試合を、後で食い違いにしない)。
- **中断**: 雷・雨・暑さで大会全体を止め、閲覧ページの上部に帯を出す。再開すると、中断した分(5 分単位に切り上げ)だけ全部門の未開始の試合をずらし、その日の終了時刻を過ぎる試合を知らせる。

### 訂正の影響を先に見せる

確定済みの結果を直すと、順位と下流の組み合わせが変わることがある。
訂正を保存する前に、エンジンは「この訂正で変わるもの」(プール順位の入れ替わり、埋まった枠のチームの入れ替わり、すでに始まった試合への影響)を計算して画面に出す。
すでに結果の出た下流の試合に影響する訂正は、運営者が明示的に承認しない限り保存しない。

## 日程とコートの自動割り当て

入力は、開始時刻、試合の間隔(スロットの長さ。参照サイトでは大会ごとに 15〜90 分)、使えるコートの一覧(配信用など属性つき)、同じチームの試合の間に空けるスロット数(7 人制は 1 以上、4on4 は 0 を許す)、段の間に空けるスロット数である。

生成の順序は次のとおり。

1. 段ごとに、試合の論理順序(ラウンド)を決める(プールは前述の固定順、トーナメントは回戦順)。
2. 参照サイトの運用に合わせ、グループを 2 つずつ組にして全コートへ並べ、終わったら次の組へ進む。
3. 同じチームの連戦と休憩の制約を満たすように、スロットとコートを割り当てる。満たせないときは、どの制約をどれだけ破ったかを一覧にして出す(生成を止めない)。
   コートは大会で共有するので、同じ大会の他のディビジョンの試合が使うコートと時間は「ふさがっている」として避ける(その試合の長さは、そのディビジョンの時間割の枠の長さ。時間割の無いディビジョンはこちらの枠の長さとみなす)。再検査でも他のディビジョンの試合との重なりを `court_conflict` として出す。
4. 運営者は日程表の上で試合をドラッグして入れ替えられる。入れ替えのたびに制約を再検査する。

当日の遅延と中断には、「このコートの以降の試合を N 分遅らせる」「全体を N 分遅らせる」の 2 つの操作で対応する。
試合の論理順序は変えず、時刻だけを再計算する。

## 監査ログ

スコア、試合の状態、順位の指定、段の確定、日程の変更は、誰がいつ何を何から何へ変えたかを記録する。
2018 年の USAU では、運営側の誤った口頭指示でスコアが書き換えられ、4 チームの主将が処分された(運営実務の調査 5.3)。
記録が残っていれば、こうした争いを事実で処理できる。

## データモデルへの追加

既存のスキーマ(`divisions`、`groups`、`matches`、`group_teams`)を壊さずに足す。

| 追加 | 内容 |
|---|---|
| `division_formats` | ディビジョンの形の指定(テンプレート名とパラメータ、タイブレーク設定、日程の設定)。JSONB と版番号 |
| `stages` | 段(ディビジョン、順番、名前、状態:準備中/進行中/確定待ち/確定) |
| `groups.stage_id` | グループが属する段 |
| `group_slots` | 枠(グループ、位置、出どころ JSONB、確定したチーム) |
| `matches.left_slot_id` / `right_slot_id` | 試合の左右がどの枠か。既存の `left_placeholder_*` は試合の勝者・敗者の出どころとして引き続き使う |
| `matches.result_type` | 通常、没収、不成立、未消化 |
| `group_rank_decisions` | 未決の同順位を運営者が決めた記録(理由つき) |
| `audit_log` | 監査ログ |

閲覧ページと API の形は変えない。
エンジンが作るのは、閲覧ページが既に表示できるグループ、試合、トーナメントの格子、未確定チーム表記である。

### 保存の形(00005_division_formats.sql)

上の表を次のように実装した。`matches.result_type` と `audit_log` は記録係画面の担当が 00004 で足す。

| 表・列 | 実装 |
|---|---|
| `division_formats` | 主キーはディビジョン。`template`、`params`(下の JSON)、`start_letter`(最初のグループ文字)、`tiebreak`(`current` / `current_no_h2h` / `jfda`)、`band_rule`(`per_game` だけ)、`forfeit_winner_score` / `forfeit_loser_score`(初期値 15-0)、`schedule`(時間割の設定)、`version`(適用のたびに 1 増える) |
| `stages` | `stage_index`、`name`、`confirmed_at`、`confirmed_unplayed`(未消化のまま確定)。状態は保存せず、結果から毎回計算する |
| `groups` | `stage_id`、`format_index`(Plan の中のグループの序数)、`confirmed_at`、`confirmed_unplayed`(プールの確定) |
| `group_slots` | `position`、`source`(出どころの JSON)、`team_id`(確定したチーム) |
| `matches` | `left_slot_id` / `right_slot_id` |
| `group_rank_decisions` | グループの順位(`group_id`)か段の全体順位(`stage_id` と `band_rank`)の指定。`team_ids` は上位から並べた JSON 配列、`reason` は決め方 |

段、グループ、試合の対応は保存せず、`template` と `params` から Plan を作り直して試合 CD とグループの序数で引く(Generate は決定的)。
プールの間のチームの入れ替えは、シード順の入れ替えとして扱う(蛇行の配置は変えない)。

### 形の指定の JSON

`division_formats.params` と管理 API の `params` は同じ形で、キーは camelCase(`format.DecodeParams` / `EncodeParams`)。

```jsonc
// pool_bands(プール → 順位帯)
{ "teams": 12, "pools": 4, "bands": [
  { "ranks": [1], "shape": "T4", "pairing": null, "name": null },   // pairing: cross / same_rank / seeded、null は既定
  { "ranks": [2], "shape": "T4", "pairing": null, "name": null },
  { "ranks": [3], "shape": "T4", "pairing": null, "name": null } ] }
// blocks(ノックアウトブロック → 順位ごとの集約)。ranks はブロック内の順位
{ "teams": 32, "bands": [{ "ranks": [2, 3], "shape": "T8R1", "pairing": null, "name": null }] }
// round_robin(総当たり 1 段)。pools は 1 か 2、finalPoolRanks は 2 プールのとき決勝プールに進む順位
{ "teams": 8, "pools": 2, "finalPoolRanks": [1, 2] }
```

`shape` は `pool`、`T2`、`T4`、`T7`、`T8`、`T8R1`、`T12`、`T16`。
枠の出どころ(`group_slots.source`)は `{"kind":"seed","seed":3}`、`{"kind":"group_rank","group":0,"rank":1}`、`{"kind":"match","match":"E2","outcome":"win"}`、`{"kind":"band_rank","stage":0,"rank":2,"order":1}`、`{"kind":"manual"}`(`group` と `stage` は形の中の序数)。

時間割の設定(`division_formats.schedule`):

```jsonc
{ "date": "2026-11-14", "start": "09:00", "slotMinutes": 60, "courts": ["1", "2", "3", "4"],
  "teamRestSlots": 1, "stageGapSlots": 0, "end": "17:00",
  // 複数日の大会(00005 の後に足した。無ければ date、start、end の 1 日)
  "days": [{ "date": "2026-11-14", "start": "09:00", "end": "17:00" },
           { "date": "2026-11-15", "start": "09:00", "end": "17:00" }],
  "lunch": { "start": "12:00", "minutes": 60 }, "stageDays": true, "sport": "seven" }
```

複数日の時間割は次のように組む(運営者レビュー C2)。

- スロットは各日の開始から終了までを枠の長さで刻み、昼休みに重なる枠は昼休みの終わりから刻み直す。試合は日をまたがない。
- 「段ごとに日を分ける」では、段 k を k+1 日目の最初から始め、最後の段以外はその日のうちに置けるかを先に試す(段が日数より多ければ、残りの段は最後の日)。
- 会場の時間に置けない試合は、休みを緩めて置き、それでも無理なら最後の日の終了の後に置いて「17:00 までにあと 6 試合が収まりません」と出す(形の提案は、収まる候補を先に並べ、収まる候補の先頭を勧める)。
- 検査は、その日の終了を過ぎる(`after_end`)、会場を使う日でないか開始前(`outside_hours`)、昼休みに重なる(`break`)、段の日に入っていない(`stage_day`)を違反にする。当日の再検査は終了時刻を見ない(遅れで超えるのは普通)。

### 進行の反映(store/format_progress.go)

- 試合の結果が変わるたびに(`advanceFromResult` の最後)、ディビジョンの形を解決し直して、枠のチーム、未試合の試合の左右、グループのチーム、最終順位(`teams.final_rank`)を書く。既に始まった試合の左右は変えない。
- プールの順位は `group_teams.rank_override` にも書き、閲覧ページの順位表にエンジンの順位(タイブレークの設定と運営者の指定を反映したもの)を出す。
- 確定後の訂正で順位が変わり、既に始まった下流の試合の対戦が食い違ったときは、自動では直さず進行画面に「食い違い」として出す(枠の側も、前の試合の勝者・敗者を待つ側も)。運営者は「順位どおりに差し替える」を選べる。
- 結果のある試合の勝者と敗者は、その試合に記録した対戦チーム(試合の行の左右)で決める。計算上の対戦チームと食い違う試合の結果は、食い違いが解消するまで次の試合へ流さず、その試合のグループの順位を出どころにする枠と最終順位にも使わない(訂正の後に、決勝に出ていないチームを優勝として書かないため)。食い違いのあるプールは確定できない。
- 結果を変える全経路(得点経過、状態、結果の種類、訂正)で影響を計算し、合っていた結果のある下流の試合が食い違いになるなら、運営者が下流の扱いを選ばない限り保存しない。扱いは「下流の試合を未試合に戻す(結果と得点経過を消し、訂正後の順位のチームで組み直す)」か「食い違いとして残す(本部が差し替えるか結果を直す)」。既に食い違っている試合は、前の承認で扱いが決まっているので承認の対象にしない。
- 対戦チームが決まる前の試合には、どの経路でも結果を入れない。
- 結果の更新、形の操作(確定、順位の指定、差し替え)、形の適用は、先にディビジョンの行をロックして直列にする(順序は大会 → ディビジョン → 試合)。下流の試合のチームを書くのは未試合の試合だけで、読んだ後に始まった試合は食い違いとして残す。
- 形の適用は、結果の入った試合が 1 つでもあれば断る(大会が始まった後に作り直さない)。

## 実装の置き場所

- `apps/api/internal/format`:純粋な Go のパッケージ。テンプレートからの生成、タイブレーク、出どころの解決、影響の計算、日程の生成。GORM と HTTP を知らない。
- `apps/api/internal/store`:生成結果の保存と、確定・訂正のトランザクション。試合の状態を変える関数は既存の試合更新関数を通す(LINE 通知のために 1 か所に集める方針。scoreview-design 8 章)。
- 管理画面:形の選択(ウィザード)、生成結果のプレビュー、日程表の編集、当日の進行画面、確定と訂正。

### 実装で決めたこと(internal/format)

本書から足した点、推測で決めた点を記録する。根拠の薄いものはコードのコメントにも「推測」と書いた。

- トーナメントの型に T2(1 試合で 1・2 位を決める)を足した。2 プールの同順位 1 戦(490 の A_k 対 B_k)を表すため。
- 帯内の組み合わせの既定:2 つの順位を 2 のべきの数のプールから集める帯はたすき掛け、1 つの順位の帯と 1 回戦のみの型は同順位どうしで隣を当てる(A1-B1、C1-D1。440 の `[A1-勝ち]` 対 `[B1-勝ち]` に合わせた推測)、プールが不揃いなら段の全体順位をシードにして標準の位置に置く。
- 現行方式は基準を辞書式に比べる(直接対決は 2 チームが並んだときだけ)。既存の `domain.RankPool` と同じ順位になることを乱数のプール 2000 個で確かめた。JFDA は一部が分かれたら最初から再適用する。
- トーナメントのグループの順位(ブロックの `A rank n`)を出どころにする枠は、確定の操作なしに試合の終了で埋まる。プールと段の全体順位だけが確定を要る。
- 結果の種類に「両チーム不戦敗」と「途中打ち切り(その時点のスコアで確定)」を足した。途中打ち切りを未消化にするときは未消化として入れる。
- 単独のトーナメント表(管理画面の `internal/bracket`)にも参照サイトの型を使えるよう、`format.BracketPlanFor` で型を `domain.BracketPlan` にし、`bracket.WithFormatTypes` で Registry に登録できるようにした(既定の Registry には入れていない)。勝者の前進の DB への反映は `store` の `advanceFromResult` が担い、`format` は解決結果を計算するだけにする。
