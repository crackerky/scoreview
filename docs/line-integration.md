# LINE 連携の設計(将来の拡張)

LINE 連携はフェーズ 3 で実装する。
本書は、フェーズ 1 と 2 の実装が LINE 連携の妨げにならないように、先に決めておく構造と、着手時に判断する材料をまとめたものである。
同じ発注者の別プロジェクト(`~/job/scoresite/docs/line-and-participants.md`)で検討した内容を、scoreview の構成(認証を Go の api が持つ)に合わせて書き直した。

## 何を LINE でできるようにするか

- **通知**：フォローしたチームの試合の開始と終了、次の試合の予定を、LINE 公式アカウントから受け取る。
- **ログイン**：記録係と運営者が LINE でログインする。チームの主将が LINE で本人確認したうえで、参加者がスコアを入力できるようにする(入力を開放するかは大会ごとの設定)。
- **導線**：公式アカウントのリッチメニューやメッセージから、大会トップ、スケジュール、試合ページを LINE アプリ内のブラウザ(LIFF)で開く。

得点ごとの配信はしない。
配信は通数で課金され、1 大会 60 試合で得点ごとに配信すると、フォロワー数十人でも無料枠を使い切るためである[^line-plan]。

## フェーズ 1 から守る構造

LINE 連携の着手時に作り直しが起きないよう、次の 4 点をフェーズ 1 の実装で守る。

### 試合の状態とスコアの変更を 1 か所に集める

通知は「試合が始まった」「試合が終わった」という状態の変化をきっかけに配信する。
状態を変える経路が管理画面、取込ツール、将来の参加者入力と複数あると、通知の積み忘れが起きる。
そこで、試合のスコアと状態を変える処理は store の 1 つの関数群(試合イベントの追加、状態の変更)だけが行い、ハンドラや取込ツールから `matches` を直接更新しない。
LINE 連携のときは、この関数のトランザクションの中で通知ジョブを積む処理を足すだけで済む(トランザクションの外で配信すると、ロールバックした変更を通知してしまう)。

取込ツールは過去の大会を一括で入れるので、通知を積まない経路として区別する。

### 認証をパスワード専用の形にしない

セッションはユーザー ID に結びつけ、ログイン方法には結びつけない(`sessions` は `user_id` だけを持つ。現状どおり)。
LINE ログインの追加時は、次のマイグレーションを足す。

- `user_identities`(user_id, provider, subject):LINE のユーザー ID(`sub`)をここに持つ。1 人のユーザーがパスワードと LINE の両方でログインできる。
- `users.email` と `users.password_hash` を NULL 許可にする。LINE ログインではメールアドレスが取れないことがある(取得には LINE Developers での申請が要る)。

api のログイン処理は「本人確認(パスワード照合、または LINE の認可コードの検証)→ ユーザーの特定 → セッション発行」の 3 段に分け、本人確認の部分だけを差し替えられる形で書く。
ただしフェーズ 1 ではパスワードしかないので、差し替えのためのインターフェースは作らない。
LINE を足すときに、この 3 段の境目で分ければよい。

### URL を安定させる

LINE のメッセージやリッチメニューに埋め込んだ URL は、送った後に変えられない。
ページの URL は参照サイトと同じ体系(`/scview/{大会ID}`、`/pscore/scv_match/open/{試合ID}?lang=jp`)で固定し、フェーズ 2 で見た目を作り変えても URL は変えない。

### 大会をまたいでチームを束ねる余地を残す

参照サイトに合わせて、チームは大会ごとに別 ID で持っている(同じクラブでも大会ごとに別の行)。
そのため「このチームをフォローする」と言ったとき、フォローの対象は大会ごとのチームではなく、大会をまたぐクラブでなければならない。
LINE 連携の前に `clubs` を足し、`teams.club_id`(NULL 許可)で大会ごとのチームを束ねる。
フェーズ 1 では作らないが、チームの登録画面と取込ツールは、後から `club_id` を一括で埋められるように、正式名を加工せずに保存する。

## 構成

```
LINE プラットフォーム ──Webhook──▶ web(/line/webhook)──内部──▶ api(署名検証、友だち状態の記録)
                                                                      │
api(試合の状態変更)── 同じトランザクションで ──▶ notification_jobs ◀─┘
                                                     │
Vercel Cron ──▶ web(/cron/notify)──内部──▶ api(ジョブを読み、Messaging API で配信)
```

- api はインターネットに公開しない方針のままにする。Webhook と Cron は web の Route Handler で受け、内部トークンを付けて api に渡す。
- Webhook の署名(`X-Line-Signature`。チャネルシークレットによる HMAC-SHA256)は api で検証する。web は本文を加工せずにそのまま渡す(加工すると署名が合わなくなる)。
- Cron の要求は `CRON_SECRET` で検証する。

## 追加するテーブル

| テーブル | 主な列 | 用途 |
|---|---|---|
| `user_identities` | user_id, provider, subject | LINE のユーザー ID |
| `clubs` | id, name_ja, name_en | 大会をまたぐチームのまとまり |
| `follows` | user_id, club_id | 通知の対象 |
| `line_friends` | line_user_id, followed_at, blocked_at | 公式アカウントの友だち状態(Webhook で更新) |
| `notification_jobs` | id, user_id, kind, payload, status, attempts, sent_at, error | 配信キュー |
| `team_members` | team_id, user_id, role(captain, member), status | 参加者入力のためのチーム所属 |

`tournaments` には参加者入力の可否(`score_entry_policy`)を足す。

## 着手時に確かめること

- LINE Login のチャネルと公式アカウント(Messaging API のチャネル)を同じプロバイダーの下に作ると、ユーザー ID が一致するか。一致しなければ、ログインで得た ID を配信先に使えない。
- Web のログインで発行される ID トークンの署名方式(HS256 か ES256 か)[^line-hs256]。api では ID トークンを使わず、ユーザー情報エンドポイントから `sub` を取る方式にすれば、署名方式に依存しない。
- 公式アカウントの料金プランと通数。2026 年 10 月に追加メッセージの単価が改定されるため、契約時点の料金表で試算する[^line-plan]。
- LIFF で開いたときの表示。参照サイトの見た目は幅 980px 固定なので、スマートフォン向けのレイアウト(フェーズ 2)を LINE 連携より先に済ませる。

[^line-plan]: [LINE公式アカウントの料金プラン](https://www.lycbiz.com/jp/service/line-official-account/plan/)。2026 年 9 月時点の公表値は、無料プランが月 200 通、ライトプランが月 5,000 通、スタンダードプランが月 30,000 通。契約前に再確認する。
[^line-hs256]: [Get profile information from ID tokens | LINE Developers](https://developers.line.biz/en/docs/line-login/verify-id-token/)。
