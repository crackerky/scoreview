# LINE 連携の設計

本書は、LINE を入口にした大会運営(エントリー、通知、記録係のスコア入力)の構成を定める。
参照サイト(score.clubjr.com)の模倣ページ(`/sctnmt`、`/scview`、`/pscore`、about、guide、contact)は削除し、製品は管理画面と観戦アプリ(`/live/{大会ID}`)に絞る。
LINE 連携はその上に、参加者(チームの代表とメンバー)と記録係の入口として載せる。

## 何を LINE でできるようにするか

- **エントリー**：チームの代表が LINE から大会に申し込み、メンバーは代表から届いた招待リンクで各自の LINE から登録する。
- **通知**：運営が管理画面から、条件で選んだ相手の個人チャットへ送る。決まった場面(スコアの未入力など)では自動でも送る。
- **スコア入力**：運営が試合ごとに決めた記録係が、LINE から記録画面を開いて入力する。
- **観戦**：メッセージやリッチメニューから観戦アプリを開く。

公式アカウントは運営会社で 1 つにする。
大会ごとに作ると、参加者に友だち追加を毎回やり直してもらうことになるためである。
使うのは今の公式アカウント(ULTIMATE PLANNING。2026 年 11 月時点で友だち 3,837 人)で、作り直さない。

参加費は当面扱わない。
支払いの確認は、これまでどおりアプリの外で運営が行う。

得点ごとの配信はしない。
こちらから送るメッセージ(プッシュ)は通数で課金され、1 大会 60 試合で得点ごとに送ると、フォロワー数十人でも無料枠を使い切るためである[^line-plan]。

## エントリーの流れ

エントリーは代表とメンバーの 2 段に分ける。
メンバー全員が本人の LINE で登録すれば、後から一人ひとりに通知を送れるためである。

```
運営     大会と部門を作る → 受付を開ける → 「送る」で告知
代表     リッチメニュー「エントリー」(またはトークで「エントリー」と送る)
         → 受付中の大会ごとに、本人用の申込リンクが返ってくる
         → 部門、チーム名、連絡先、チーム向けの質問 → 送信 → 招待リンクが出る
代表     招待リンクをチームの LINE グループに貼る(画面の「LINE で送る」から)
メンバー 招待リンク → 公式アカウントのトークが「参加 招待コード」の入った状態で開く → 送る
         → 本人用の登録リンクが返ってくる → 名前、背番号、メンバー向けの質問
メンバー 登録した後に「エントリー」と送ると、返信の「メンバーの方」に、登録したチームの登録リンクが返る
         (返信は「チームの代表の方」と「メンバーの方」に分け、登録した人にはメンバーの方を先に書く。
         メンバーが代表の申込の画面を開いて、同じチームの申込を作らないように)
運営     申込一覧で中身を確かめる → 参加を決める(または直してもらう)→ 部門のチームと選手ができる
```

### 代表エントリーとメンバーエントリー

- **代表エントリー**：チームについての申込。部門、チーム名(正式名と短縮名)、代表の連絡先、チーム向けの質問への答えを持つ。送信すると、チーム専用の招待コードを発行する。
- **メンバーエントリー**：メンバー一人ひとりの登録。招待リンクから本人の LINE で開き、名前、背番号、メンバー向けの質問に答える。

メンバーエントリーは出場の条件にしない。
代表がメンバー表に名前を直接書いてもよく(補填)、その行には後からメンバー本人が招待リンクで自分の LINE を結びつけられる。
結びつけるときは、代表が書いた行の名前と背番号を、本人が確かめて直す形にする。
運営と代表には、チームごとに「8 人中 6 人が LINE で登録済み」のような進み具合を出す。

LINE の個人チャットに送れるのは、公式アカウントを友だちに追加している人だけである。
代表もメンバーも、公式アカウントのトークに送ったメッセージから申込に入るので、登録の流れの中で友だち追加まで済む。
送る画面では、友だちでない人(ブロックした人を含む)を「届かない人」として数える。

### 申込とチームを分ける

申込は `teams` とは別のテーブルに持ち、運営が承認したときに初めて `teams` と `players` の行を作る。
`teams` は大会の形のエンジンと組分けが読むので、承認前や取り消した申込が混じると、組の数やシードが狂うためである。
申込の状態は次の 4 つにする。
画面と LINE の文では、運営と代表に通じる言葉(確認待ち、直し待ち、参加決定、取消)で出す。
コードと api では pending、returned、approved、cancelled と呼び、この文書では承認、差し戻しとも書く。

- **確認待ち**(pending)：代表が送信し、運営の確認を待っている。
- **直し待ち**(returned、差し戻し)：運営が直してほしい点を付けて代表に返した。代表が直して送り直すと確認待ちに戻る。
- **参加決定**(approved、承認)：`teams` と `players` ができた。以後のメンバーの追加と修正は、`players` にも反映する。
- **取消**(cancelled)：代表または運営が取り消した。承認した申込は取り消さず、既存の棄権(`team_withdrawals`)でチームを外す。チームがもう組分けと試合に入っているかもしれないためである。

申込の決まり(中身と答えの検査、状態の移り方、承認で作るチームと選手の形)は api の `internal/entry` に置き、LINE からの申込も管理画面の代理入力も同じ受付を通す。
代理入力は、電話や紙で受けた申込を運営が入れる経路で、LINE の受付より先に作った(LINE の設定を待たずに、質問、申込一覧、承認を運営が試せるようにするため)。
同じ部門に同じチーム名の取り消していない申込は二重に入れない(確認の画面から戻って送り直した申込を弾く)。

### フォームの項目

フォームは 2 層にする。

- **共通の項目**：部門、チーム名、代表の連絡先、メンバーの名前と背番号。コードで固定し、どの大会でも同じ列に入る。
- **大会ごとの質問**：運営が大会ごとに足す。「チーム向け」か「メンバー向け」かを選び、形式(短い文、長い文、選択、数、はい/いいえ)と必須かどうかを決める。

共通の項目を質問として持たないのは、チームと選手の行を作るときに必ず要る値だからである。

### 参加者の台帳

公式アカウントに話しかけた人(友だちの追加、メッセージ)は、`line_users` に自動で載る。
申込とメンバー登録のたびに、そのとき入れた名前と連絡先を、その人の前回の入力として同じ行に残す(メンバー登録は名前だけで、代表として入れた連絡先は消さない)。
次に申込の画面を開くと、代表の名前、電話番号、メールアドレスに前回の入力が最初から入る。

前に申し込んだチームは、その人が代表として出した申込から取り出す(今の大会の申込は除き、同じチーム名は最後の申込だけ、新しい順に 10 まで)。
チーム名を候補から選ぶか書いて合うと、短縮名とメンバー表が入る。
メンバー表は、その申込の今のメンバーなので、メンバーが本人登録で直した名前と背番号がそのまま入る。
チームの台帳を別に持たないのは、出した申込がすでにチーム名とメンバーを持っていて、別に持つと食い違うためである。

### 代表への知らせ

LINE から出した申込の代表には、受付、送り直しの受付、承認、差し戻し、取消を、公式アカウントから知らせる。
受付の知らせには、メンバーへの登録のお願い(招待リンク)を別の吹き出しで付け、代表がそのままチームの LINE グループに転送できるようにする。
差し戻しの知らせには運営が書いた理由を付け、承認の知らせにはスコアサイトの大会の URL を付ける。

知らせは返信ではないので push で送り、公式アカウントの月の配信数に数えられる(1 回の送信は吹き出しが 5 つまでで 1 通)。
ブロックしている人には送らない。
知らせは申込の記録とは別に送り、送れなくても申込と運営の操作は失敗にせず、エラーをログに残す。
運営が代わりに入れた申込には、代表の LINE が無いので知らせない。

### 大会をまたぐクラブ

チームは大会ごとに別の行で持っているので、代表の LINE を大会ごとのチームに結びつけると、次の大会で何も引き継げない。
今は、上の「参加者の台帳」の前に申し込んだチームで、同じ代表が続けて申し込むときの下書きを作っている。
代表が替わってもチームを引き継ぎたいとき、または通知の宛先を「前に出たクラブの代表」で選びたいときに、`clubs` を足し、代表エントリーと `teams` をクラブに結びつける(`teams.club_id` は NULL 許可)。

## 管理画面から送る仕組み

通知は、どれも「条件で宛先を選び、文面を確かめて送る」という同じ形をとる。
そこで送る仕組みを 1 つ作り、宛先の条件を増やしていく。

| 場面 | 宛先の条件(例) | 送り方 |
|---|---|---|
| 大会を作った(告知) | 友だち全員、前に出たクラブの代表 | 手動 |
| エントリーの確認 | 承認待ちの代表、本人登録が揃っていないチームの代表、未登録のメンバー | 手動 |
| 個人チャットへの通知 | 選んだチーム、選んだ人 | 手動 |
| スコアの催促 | 終わった試合のスコアを入れていない記録係 | 自動と手動 |
| 記録係の割り当て | その試合の記録係 | 自動 |

宛先の条件は、コードで名前を付けた条件にし、管理画面から自由な SQL は書かせない。
管理画面から DB を自由に読めると、宛先の選び方に権限の確認が効かなくなるためである。

送る前の画面には、次を出す。

- 文面の見本(実際に届く形)
- 宛先の人数と、友だちでないため届かない人数
- 今回使う通数(プッシュは通数で課金されるため)

送ったら送信履歴に残す。
履歴は、送った人、条件、文面、宛先ごとの結果(届いた、届かなかった、失敗)を持つ。

今ある条件は、大会の画面から選ぶ次の 4 つである(api の `internal/notify`)。

- 申し込んだ代表(取り消した申込を除く。申込の状態と部門で絞れる)
- メンバーの登録が揃っていない代表
- 承認したチームの代表と、LINE で登録したメンバー
- 前の大会に申し込み、この大会にはまだ申し込んでいない代表(受付を始めた知らせ)

どれも LINE から申し込んだ人だけで、運営が代わりに入れた申込の代表には送れない。
同じ人は 1 人にまとめ、届く文の 1 行目には大会名を付ける(大会をまたいで申し込んでいる人が、どの大会の話かを取り違えないように)。
手動の「送る」は、宛先を 500 人ずつのまとまりに分け、まとまりごとに LINE の送り直しのキー[^line-retry]を決めて記録してから、同じ要求の中でマルチキャストで送り、宛先ごとの結果を書く。
送る画面を開くたびに作る乱数で同じ送信を 2 回記録しないので、押し直しや応答の前の再送では送られない。
今月の残りの配信数が足りなければ、一部の人にだけ届くのを避けるため、何も送らない。

LINE は、送り直しのキーが同じ要求をもう受け付けていれば送らずに 409 を返すので、受け付けたかが分からない失敗(LINE の 5xx、応答が無い)は、同じキーですぐ 1 回だけ送り直す。
LINE が受け付けなかったと分かる失敗(4xx)は、送り直しても結果が変わらないので、すぐには送り直さない。
送れなかったまとまりと途中で止まったまとまりは、送ってから 24 時間(キーが有効な間)、送った記録の画面から、同じキー、同じ宛先、同じ文で送り直せる。
送る側は、まとまりを送る前に 15 分の持ち時間を付けて取る(最初の送信も送り直しも)。
持ち時間の間は、ほかの送り直しがそのまとまりを送らないので、同じキーの要求が LINE に同時に届くことはない(LINE は同時に届いたときの扱いを決めていない)。
15 分は api の 1 回の要求が続きうる時間より長いので、持ち時間が切れても送っていないまとまりは、途中で止まったものとして送り直せる。
送り直しで新しい送信を作ると、前の送信が実は届いていた人に 2 回届くので、同じ条件で送り直すことは勧めない。

### 日時を決めて送る(前日と当日の案内)

送る画面では、すぐ送るほかに、日時を決めて送れる(予約)。
前日と当日の案内は、この予約のひな形として作る。
大会の日から送る日時(前日の 19 時、当日の 7 時。運営会社と決めるまでの仮の既定)を入れ、宛先を「承認したチームの代表とメンバー」にし、文のひな形(集合時刻と会場の欄、スコアサイトの大会の URL)を入れた送る画面を開く。
運営が文を確かめて書き足してから予約するので、決まった文を黙って送ることはない。

予約は宛先を持たずに記録し、送る時刻に条件で宛先を数え直す。
予約の後に承認したチームにも届き、承認の前に案内を予約しておける。
今月の残りの配信数も送る時刻に確かめ、足りなければ送らずに、送れなかった理由を記録に残す。
送るまでは、送った記録の画面から取りやめられる。

送る時刻の来た予約は、Vercel の schedules が 15 分ごとに web の `/cron/notify` を呼び、web が `CRON_SECRET` を確かめてから api に送らせる。
そのため、送る時刻から 15 分ほど遅れることがある。
予約から送ったことへの書き換えは、予約のままのときだけ効く 1 回の書き換えで行うので、呼び出しが重なっても 1 回だけ送る。

スコアの催促のような、条件で自動に積む送信は、まだ作っていない。
作るときは同じ定期の呼び出しで、たとえば「試合の予定終了時刻から N 分たっても結果が入っていない」で積み、同じ試合に同じ催促を二度送らないよう、送信履歴で重複を弾く。
N をはじめとする自動送信の時刻は、運営会社と決める。

## 記録係のスコア入力

運営は、試合ごとに記録係を決める。
割り当ては既存の `staff_assignments`(試合単位、またはコートと時間帯の単位)をそのまま使い、記録係が LINE で入力するための新しい表は作らない。
同じ試合を 2 台で記録しないための `match_scorers`(いま記録している端末)も、そのまま使う。

記録係は、割り当てが決まった時点と試合の前に、LINE で試合の案内(相手、コート、時刻、記録画面へのリンク)を受け取る。
試合が終わってもスコアが入らなければ、前節の催促がその記録係に届く。

今の記録係は、運営が管理画面で作る `users`(role は staff)である。
これに加えて、参加が決まったチームの代表が、LINE で登録したメンバーから 1 人を記録係に選べる(`team_entries.scorer_member_id`)。
選ばれたメンバーには、記録係になったことを公式アカウントから知らせる。
チームの記録係は、公式アカウントに「記録」と送ると返ってくる本人用のリンク(purpose は scorer)から記録の画面に入る。
入るときに、その LINE の人に結んだ `users`(role は staff、`team_scorer` が真、パスワードは持たない)を用意して大会の担当にし、セッションを発行する。
チームの記録係が記録できるのは、自分のチームの試合のうち、自分のチームが記録する試合だけである(左のチームに記録係がいれば左、いなければ右。時間割で上に書いてあるチームを先にする)。
代表が記録係を選び直したり外したりすると、前の記録係はリンクで入れず、試合も記録できなくなる。

## 本人の確かめ方

申込とメンバー登録では、操作している人が公式アカウントのどの友だちかを知る必要がある。
後で個人チャットに送るときの宛先が、公式アカウントから見たユーザー ID だからである。

### 公式アカウントの今の状態

今の公式アカウントの Messaging API(チャネル ID 1656569904)は、Lイベントを入れたときに Lイベントの提供元の側で有効にされ、Webhook も Lイベント(`https://www.l-event.me/callback`)に向いている。
運営会社のどの LINE アカウントで LINE Developers に入っても、このチャネルの入ったプロバイダーは見えない。
プロバイダーは後から変えられない[^line-provider]。
ユーザー ID はプロバイダーごとに違う値になるので[^line-provider-design]、運営会社のプロバイダーに LIFF(LINE ログイン)を作っても、そこで得た ID は公式アカウントから見た ID と一致しない。

チャネル ID とチャネルシークレットは、公式アカウントの管理画面(Official Account Manager の 設定 → Messaging API)で運営会社の管理者が見られる。
この 2 つでチャネルアクセストークンを発行できるので、送ることは運営会社の側からでもできる。

### Webhook で本人を確かめる

そこで、本人の確認は LIFF ではなく Webhook で行う。
公式アカウントに届くメッセージとポストバックには、公式アカウントから見たユーザー ID が付いている。
そのメッセージへの返信で、本人用のリンク(推測できない合言葉を入れた URL。期限までは何度でも開ける)を返す。

| | 本人用のリンク(採用) | LIFF |
|---|---|---|
| 得られる ID | 公式アカウントから見た ID(送るときの宛先と同じ) | LINE ログインのチャネルのプロバイダーでの ID |
| 前提 | 公式アカウントの Webhook をこちらで受ける | 公式アカウントと同じプロバイダーに LINE ログインのチャネルを作れる |
| リンクを転送されたとき | 転送された人も、元の人として入力できてしまう | 開いた人本人として扱う |
| 手間 | 申込の前に、トークで 1 往復する | LIFF の SDK と LINE ログインのチャネルが要る |

リンクの転送には、有効期限(3 日)で備える。
期限が切れたら、もう一度「エントリー」と送れば新しいリンクが返る。
Lイベントの提供元から、そのプロバイダーの権限をもらえた場合は、同じプロバイダーに LIFF を作って入口を差し替える(申込の画面はそのまま使う)。

本人用のリンクの合言葉は、平文を保存せず SHA-256 だけを保存する(セッションのトークンと同じ扱い)。

## Lイベントからの移行

Webhook の宛先は 1 つしか設定できない[^line-multi-tools]。
こちらで Webhook を受けた時点で Lイベントは動かなくなるので、両方を同時には使えない。
移行は次の順に進める。

1. 運営会社のプロバイダー(Ultimate planning score site)の下に、試験用の公式アカウントを作り、Webhook をこちらに向ける。申込、承認、送る、を試験用の公式アカウントで何回でも試す。今の公式アカウントと Lイベントには触れない。試験は本番と同じ DB で行うので、試験用の大会を使い、終わったら試験で作った申込と、試験用の公式アカウントの `line_users`(公式アカウントごとにユーザー ID が違うので、切り替えた後の公式アカウントでは使えない)を消す。
2. 受付の無い時期を選び、今の公式アカウントの Webhook URL を、公式アカウントの管理画面からこちらに書き換える。友だちはそのまま引き継がれる。
3. リッチメニューを、こちらの「エントリー」に差し替える。
4. Lイベントを解約する。そのとき、Messaging API のチャネル(提供元のプロバイダーの中にある)を消さないよう提供元に頼む。チャネルが消えると、公式アカウントから送れなくなるためである。

### 前の大会の参加者を移す

Lイベントの書き出し(大会ごとに「代表者のみ」と「選手全員」の CSV)を、前の大会として取り込む(api の `cmd/importlevent`)。
書き出しの UID は、Lイベントが使う公式アカウントのチャネルから見たユーザー ID なので、Webhook をこちらに切り替えた後に届く ID と同じになる。
取り込んでおくと、切り替えの直後から、前に申し込んだ代表が「エントリー」と送れば前のチームと前回の名前と連絡先が申込の画面に入り、運営は「前の大会に申し込んだ代表」に受付の知らせを送れる。

取り込む大会は、終わった、一覧に載せない大会として作り、申込は LINE から受けた承認済みの申込にする(チームと選手は作らない)。
参加者の台帳(`line_users`)には、名前、代表のメールアドレス、ユーザー ID だけを入れる(代表のメールアドレスを選手全員の書き出しでだけ聞いた大会は、代表本人の行から取る)。
書き出しにある生年月日、性別、LINE の表示名は、このサイトが扱う情報に入れていないので取り込まない。
台帳の名前と連絡先は、取り込む申込のほうが新しいか同じ時刻のときだけ書き換える(同じ書き出しを読み直して取り込み直せば、読み直した中身になる)。

メンバーの書き出しのチーム名は「チーム名(部門)」と書かれ、代表の書き出しと表記が揺れるので、空白、大文字小文字、括弧、記号、語の順の違いは同じチームとして結ぶ。
それを超える違い(カタカナと英字、打ち間違い)は、取り込む人が `-alias` で言い換えを渡す。
同じ部門に同じチームの申込が 2 件あれば、最初の申込に寄せる。
既定では読むだけで、チーム名と人数と、確かめてほしいこと(寄せた申込、申込の見つからないメンバー)を出し、`-apply` を付けたときだけ書く。

切り替えの前は、本番の LINE の設定が試験用の公式アカウントなので、取り込んだ人には送れない(試験用の公式アカウントからは、別のプロバイダーのユーザー ID に届かない)。

チャネルアクセストークンは、送るたびに 15 分だけ有効なステートレスのトークンを発行して使う[^line-token]。
長期のトークンは 1 つのチャネルに 1 つしか持てず、発行し直すと前のものが無効になるので、移行の前に発行すると Lイベントが止まる。

## URL

LINE のメッセージやリッチメニューに埋め込んだ URL は、送った後に変えられない。
そこで、次の URL を固定する。

| URL | 画面 |
|---|---|
| `/` | 受付中と開催中の大会の一覧 |
| `/live/{大会ID}` | 観戦アプリ |
| `/tournaments/{大会ID}` | スコアサイト |
| `/entry/{合言葉}` | 本人用のリンクで開く、代表の申込とメンバーの登録 |
| `/line/webhook` | 公式アカウントの Webhook の受け口 |

メンバーの招待リンクは、公式アカウントのトークに文を入れた状態で開く LINE の URL(`https://line.me/R/oaMessage/{ベーシック ID}/?参加%20{招待コード}`)にする[^line-url-scheme]。
招待コードは推測できない長さの乱数にする。

## 先に守る構造

次の 3 点は、LINE 連携の前から守る。

### 試合の状態とスコアの変更を 1 か所に集める

通知は「試合が始まった」「試合が終わった」という状態の変化をきっかけに積む。
状態を変える経路が管理画面、LINE の記録画面と複数あると、通知の積み忘れが起きる。
そこで、試合のスコアと状態を変える処理は store の 1 つの関数群(試合イベントの追加、状態の変更)だけが行い、ハンドラから `matches` を直接更新しない。
通知ジョブは、この関数のトランザクションの中で積む(トランザクションの外で積むと、ロールバックした変更を通知してしまう)。

### 認証をパスワード専用の形にしない

セッションはユーザー ID に結びつけ、ログイン方法には結びつけない(`sessions` は `user_id` だけを持つ。現状どおり)。
LINE の参加者は `line_users` に持ち、`users` とは分ける。
参加者は管理画面にログインしないので、申込とメンバー登録は本人用のリンクの合言葉だけで行う。
LINE で入力する記録係を作るときは、`line_users.user_id` で `users` と結び、記録係の権限はこれまでどおり `users` で決める。

api のログイン処理は「本人確認(パスワード照合、または本人用のリンクの合言葉)→ ユーザーの特定 → セッション発行」の 3 段に分け、本人確認の部分だけを差し替えられる形にする。

### api を公開しない

api はインターネットに公開しない方針のままにする。
LINE の Webhook と、自動送信のスケジュールは web の Route Handler で受け、内部トークンを付けて api に渡す。

## 構成

```
LINE プラットフォーム ──Webhook──▶ web(/line/webhook)──内部──▶ api(署名検証、友だち状態の記録、本人用のリンクの返信)
本人用のリンクのページ ──合言葉──▶ web ──内部──▶ api(合言葉の確認、申込とメンバー登録)

管理画面の「送る」──▶ web ──内部──▶ api(宛先を選んで記録し、Messaging API で送って結果を書く)
api(試合の状態変更)── 同じトランザクションで ──▶ notification_jobs
                                                                         │
Vercel schedules(15 分ごと)──▶ web(/cron/notify)──内部──▶ api(送る時刻の来た予約を、そのときの宛先に Messaging API で送る)
```

- Webhook の署名(`X-Line-Signature`。チャネルシークレットによる HMAC-SHA256)は api で検証する。web は本文を加工せずにそのまま渡す(加工すると署名が合わなくなる)。
- 定期の呼び出しは、web が `CRON_SECRET` で検証する。

## 追加するテーブル

| テーブル | 主な列 | 用途 |
|---|---|---|
| `line_users` | line_user_id, friend, followed_at, unfollowed_at, user_id(NULL 可), name, phone, email, profile_updated_at | 公式アカウントから見た LINE のユーザーと友だち状態(Webhook で更新)、前回の入力(参加者の台帳)。記録係にするときに `users` と結ぶ |
| `line_webhook_events` | webhook_event_id, received_at | 同じイベントが 2 回届いたときに 2 回処理しない |
| `entry_links` | token_hash, line_user_id, purpose(team, member), tournament_id または team_entry_id, expires_at | 本人用のリンク |
| `clubs` | id, name_ja, name_en, owner_line_user_id | 大会をまたぐチームのまとまり(持ち主は代表の LINE の人) |
| `entry_questions` | tournament_id, scope(team, member), label, kind, required, options, sort_order | 大会ごとの質問 |
| `team_entries` | tournament_id, division_id, club_id, rep_line_user_id, 共通の項目, status, invite_code, team_id | 代表エントリー(承認で team_id が入る) |
| `member_entries` | team_entry_id, line_user_id(NULL 可), name, number, player_id | メンバーエントリー(代表が書いた行は line_user_id が空) |
| `entry_answers` | question_id, team_entry_id または member_entry_id, value | 質問への答え |
| `notification_batches` | id, tournament_id, request_key, audience, body, automatic, sent_by, created_at | 送信履歴(1 回の「送る」。audience は宛先の条件、body は届けた文) |
| `notification_jobs` | id, batch_id, line_user_id, name, teams, status, error, sent_at | 宛先ごとの結果(宛先は公式アカウントから見た LINE の人。name と teams は送った時点のもの) |

既存のテーブルには次を足す。

- `teams.club_id`(NULL 許可)
- `users.email` と `users.password_hash` の NULL 許可、`users.role` に member
- `tournaments` に受付の期間と状態

記録係の割り当ては既存の `staff_assignments` と `match_scorers` を使い、新しい表は足さない。

## 着手時に確かめること

試験用の公式アカウントで、次を確かめてから今の公式アカウントを切り替える。

- 本人用のリンクで申し込み、承認した人に、公式アカウントから個人チャットで届くか。
- 招待リンクから、友だちでない人がトークを開いたときに、友だち追加を経て「参加」を送れるか。
- iPhone と Android の LINE で、表示と動作に差がないか。
- 公式アカウントの料金プランと通数。2026 年 10 月に追加メッセージの単価が改定されたため、契約時点の料金表で試算する[^line-plan]。
